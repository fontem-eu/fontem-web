Vision: Follow the Money

The graph now knows who companies are and what they earn. The next layer is who pays them with public money, how much, and for what.

EU public procurement is one of the largest economic activities in Europe — over €670 billion per year flows through government contracts. This data is public, structured, and machine-readable. By connecting it to our company graph, we can answer questions like:

  • Which companies receive the most public money in a given country?
  • Which government bodies are the biggest spenders?
  • Are contracts being awarded through open competition or negotiated procedures?
  • Do the same companies keep winning contracts from the same authorities?
  • How do a company’s government revenues compare to its total revenue?
Long-term direction

This is the first step toward the “Eye of Horus” vision — connecting companies to people, political roles, court cases, and assets. Procurement data is the natural starting point: it’s the most structured, most complete, and most immediately actionable.

Data Source: TED (Tenders Electronic Daily)

TED is the EU’s official procurement database. Every EU government contract above a threshold value (€140K for services, €5.4M for works) must be published here.

What we get (structured XML, no PDFs)

Access methods

  • Bulk XML downloads (preferred — same approach as GLEIF, no rate limits): https://ted.europa.eu/packages/monthly/YYYY-M
  • REST API at api.ted.europa.eu (anonymous, for targeted queries)
  • CSV subset at data.europa.eu (simplified, fewer fields)

Format: eForms XML (EU-mandated standard since October 2023). Pre-2023 data uses an older TED XML schema.

Key insight: All the “juicy” metadata — who won, how much, from whom, for what — is in the structured XML. We never need to download or parse legal PDFs.

Neo4j Data Model Extension

New nodes

(:Contract {
  ted_notice_id:     string,   // primary key, e.g. "2024/S 123-456789"
  title:             string,   // contract title
  description:       string,   // truncated to ~500 chars
  value_eur:         float,    // total value in EUR
  value_currency:    string,   // original currency
  value_original:    float,    // value in original currency
  cpv_main:          string,   // main CPV code
  procedure_type:    string,   // "open" | "restricted" | "negotiated"
  notice_type:       string,   // "contract-award" | "contract-notice"
  publication_date:  string,   // ISO date
  award_date:        string,   // ISO date
  country:           string    // awarding authority country
})

(:Authority {
  authority_id:      string,   // UUID5 from "ted_auth:{country}:{name}"
  name:              string,   // official name
  country:           string,   // ISO 3166-1 alpha-2
  type:              string,   // "ministry" | "regional" | "agency"
  vat_number:        string    // nullable
})

(:CPV {
  code:              string,   // primary key, e.g. "72000000"
  description:       string,   // "IT services: consulting, ..."
  division:          string    // first 2 digits (top-level category)
})

New relationships

(:Authority)-[:AWARDED]->(:Contract)       // who issued the contract
(:Contract)-[:AWARDED_TO]->(:Company)      // who won the contract
(:Contract)-[:CATEGORIZED_AS]->(:CPV)      // what was bought

Company Matching Strategy

This is the hardest part. TED identifies companies by name + VAT. Our graph identifies by LEI. We match in four layers, from highest to lowest confidence:

1

VAT direct match

If a Company node already has vat = {vat_number} (set by a previous ETL run), link directly. O(1) index lookup.

2

GLEIF API lookup

Query api.gleif.org by registration number to find the LEI for a given VAT. If found, match to the existing Company node and set vat for future runs. Cache results to avoid re-querying.

3

Normalized name + country

Normalize the company name (uppercase, strip legal suffixes like “S.A.”, “GmbH”). Search existing nodes: WHERE c.country = $country AND toLower(c.name) = toLower($name). Link if exactly one match.

4

Create new Company node

Unmatched contractors become new nodes via gmr_id.from_national_id(country, vat) or gmr_id.from_name(country, name). These exist purely from procurement data — linkable later when they appear in GLEIF.

Expected match rate: ~20% of unique contractors will match existing GLEIF Company nodes. But these represent ~65% of total contract value — the big companies (SAP, Thales, Bouygues) are in GLEIF. Smaller local firms (local construction, cleaning services) will be new nodes.

Implementation Phases

PHASE 5 Data Model Spike

Validate the model before writing production code.

  • Download 1 month of TED data (e.g. 2024-06)
  • Parse the eForms XML — confirm field extraction works
  • Load Contract + Authority + CPV nodes into local Neo4j
  • Validate query patterns: Company → contracts, Authority → contracts, CPV aggregations
  • Load CPV reference taxonomy (~9,000 codes, one-time)
PHASE 6 ETL Pipeline

Follow the patterns established by load_gleif.py: streaming, batched, idempotent.

New files:

src/etl/
  load_cpv.py              # one-time CPV taxonomy (~9K codes)
  ted_parser.py            # streaming eForms XML parser
  ted_matcher.py           # company matching (layers 1-4)
  load_ted_contracts.py    # main: download, parse, match, MERGE

load_cpv.py

  • Load ~9,000 CPV codes from EU published reference data
  • MERGE (:CPV {code}) with description and division
  • Run once; idempotent

ted_parser.py

  • Stream-parse eForms XML with iterparse (same approach as GLEIF)
  • Filter to Contract Award Notices only
  • Extract: title, value, CPV, buyer info, contractor info, dates, procedure type
  • Yield structured dicts — no database dependency

ted_matcher.py

  • Implement the 4-layer matching strategy
  • Cache VAT → gmr_id mappings within a run
  • Log unmatched high-value contractors for manual review

load_ted_contracts.py

  • CLI: python -m src.etl.load_ted_contracts --year 2024 --month 6
  • Range: --from 2024-01 --to 2026-03
  • Downloads monthly ZIPs, streams XML, matches companies, batches MERGE
  • Batch size: 500 (contracts are larger payloads)
  • Idempotent via MERGE (:Contract {ted_notice_id})

Deployment

CronJob: monthly on the 1st at 04:00 UTC — loads the previous month’s awards.

Indexes & Constraints

-- Constraints (unique identifiers)
CREATE CONSTRAINT contract_notice_id IF NOT EXISTS
  FOR (ct:Contract) REQUIRE ct.ted_notice_id IS UNIQUE
CREATE CONSTRAINT authority_id IF NOT EXISTS
  FOR (a:Authority) REQUIRE a.authority_id IS UNIQUE
CREATE CONSTRAINT cpv_code IF NOT EXISTS
  FOR (cpv:CPV) REQUIRE cpv.code IS UNIQUE

-- Indexes (query performance)
CREATE INDEX company_vat IF NOT EXISTS FOR (c:Company) ON (c.vat)
CREATE INDEX contract_award_date IF NOT EXISTS FOR (ct:Contract) ON (ct.award_date)
CREATE INDEX contract_country IF NOT EXISTS FOR (ct:Contract) ON (ct.country)
CREATE INDEX contract_cpv_main IF NOT EXISTS FOR (ct:Contract) ON (ct.cpv_main)

Open Questions

  1. Start year. Begin with 2024+ only (eForms format, cleanest data), or go back to 2018 (different XML schema, more work)?
  2. GLEIF API rate limits. Layer 2 matching queries GLEIF per-VAT. GLEIF free tier has rate limits. Should we batch-download the GLEIF “Registration Authorities” file instead (similar to the Level 1 dump approach)?
  3. Contract thresholds. TED only covers contracts above EU thresholds (€140K services, €5.4M works). Smaller contracts are in national portals. Is TED-only sufficient for the first version?
  4. Historical backfill priority. Load 2024 first, then go backwards? Or load everything and wait?
  5. Authority deduplication. Government bodies are identified by name, which varies across languages and abbreviations. How aggressive should we be with deduplication?
