What the API currently does:

  • Reads eu_entities.json to know which tickers are EU
  • Reads summaries/{TICKER}.json for EU financial data
  • Calls edgartools library for US financial data (EDGAR live)
  • Reads prices/daily/{TICKER}.csv for all price history
  • Routes every request by ticker using an in-memory set
Pain points
  • Company identity is a ticker string — one company, multiple listings = multiple disconnected records
  • No company entity that exists independently of a market listing
  • Companies without a resolvable ticker are invisible to the system
  • EU/US split is a routing hack, not a data model
  • No foundation for people, contracts, ownership, or any relational data

What changes:

  • The FinancialDataSource interface (already abstract) gets a new GraphDataSource implementation
  • The API response shapes do not change — the frontend is unaffected
  • Price CSVs stay on NFS, referenced by Listing.ticker
  • Neo4j holds everything else: company master records, listings, financial history

Key Architectural Principles

  1. Company-first, not ticker-first. The canonical entity is a company identified by gmr_id. A ticker is a listing attribute, not an identity.
  2. GLEIF is the company master record. For any company with a LEI, GLEIF data is authoritative for name, country, legal form, and status. We store the LEI and reference back to GLEIF.
  3. Price time series stay flat. CSVs on NFS are the right structure for OHLCV data. No graph database stores time series efficiently. The API bridges the two stores.
  4. The FinancialDataSource interface is the seam. The frontend and all business logic depend on this contract. Adding a graph backend means implementing this interface — nothing above it changes.
  5. Idempotent ETL. Every ETL script can be re-run safely. MERGE on gmr_id prevents duplicates.

Internal Company ID (gmr_id)

CIK is US-only (SEC EDGAR). LEI is the best global identifier but not universal — many companies, especially in emerging markets, lack one. We need an internal ID that works for every company on earth regardless of whether external IDs exist.

Proposal: UUID version 5 (deterministic)

gmr_id = str(uuid.uuid5(GMR_NAMESPACE, canonical_source_id))

Where GMR_NAMESPACE = UUID("6ba7b810-9dad-11d1-80b4-00c04fd430c8") (fixed, defined once) and canonical_source_id is resolved in priority order:

  1. lei:{LEI}  —  e.g. lei:549300EEJH4FEPDBBR25
  2. edgar:{zero-padded-10-digit-CIK}  —  e.g. edgar:0000320193
  3. {ISO2}:{national_registration_number}  —  e.g. gb:05765016 (Companies House)
  4. {ISO2}:{normalized_legal_name}  —  last resort, name-based

Why UUID5

  • Deterministic — same company always gets the same gmr_id regardless of run or machine
  • Standard format, works in every database, language, and URL
  • Collision-free in practice (SHA-1 namespace, 2122 space)
  • ETL idempotency: MERGE (c:Company {gmr_id: $id}) is safe to run repeatedly

Example

Telefonica SA  →  lei:549300EEJH4FEPDBBR25  →  gmr_id: "f47ac10b-58cc-5372-a567-0e02b2c3d479"
Apple Inc      →  edgar:0000320193           →  gmr_id: "3c7de3e4-1234-5678-abcd-ef0123456789"

External IDs are stored as separate indexed properties on the Company node, not encoded into gmr_id:

lei:         "549300EEJH4FEPDBBR25"   (indexed, nullable)
cik:         "0000320193"             (indexed, nullable, US only)
local_id:    "05765016"               (indexed, nullable, national reg number)
isin:        ["ES0178430E18", ...]    (list — a company can have multiple ISINs)

Data Model

Nodes

(:Company {
  gmr_id:     string,   // UUID5, primary key
  lei:        string,   // GLEIF LEI, indexed, nullable
  cik:        string,   // EDGAR CIK (zero-padded 10-digit), indexed, nullable
  local_id:   string,   // national registration number, nullable
  name:       string,   // legal name
  country:    string,   // ISO 3166-1 alpha-2
  legal_form: string,   // "SA", "PLC", "GmbH", etc.
  sector:     string,   // GICS or NACE sector, nullable
  active:     boolean   // GLEIF entity status
})

(:Listing {
  ticker:     string,   // primary key within this node type, e.g. "TEF.MC"
  exchange:   string,   // exchange suffix / MIC code, e.g. "MC"
  currency:   string,   // ISO 4217, e.g. "EUR"
  active:     boolean
})

(:FinancialYear {
  year:             int,
  source:           string,   // "ESEF" | "EDGAR"
  revenue:          float,
  gross_profit:     float,
  operating_income: float,
  net_income:       float,
  ebitda:           float,
  eps:              float,
  total_assets:     float,
  total_debt:       float,
  equity:           float,
  cash:             float,
  capex:            float,
  filing_date:      string    // ISO date of the filing
})

Relationships

(:Company)-[:LISTED_AS]->(:Listing)
// A company can have multiple listings (Madrid, NYSE ADR, Frankfurt dual-listing)
// The Listing node carries the ticker used to look up price CSVs on NFS

(:Company)-[:REPORTED {year: int}]->(:FinancialYear)
// One node per fiscal year per company; year is also on the node for easy filtering

Future nodes (out of scope for this plan, defined here for reference)

(:Person)           -[:DIRECTS | :MANAGES | :OWNS_STAKE]-> (:Company)
(:Contract)         -[:AWARDED_TO]->                        (:Company)
(:PoliticalRole)    -[:HELD_BY]->                           (:Person)
(:CourtCase)        -[:INVOLVES]->                          (:Company | :Person)
(:Asset)            -[:OWNED_BY]->                          (:Company)

Phased Plan

PHASE 0 Finalize Data Model and Tooling

Prerequisite — no code changes to production.

  • Agree on this data model (review and feedback on this document)
  • Decide on GLEIF full dump vs API for ETL (full dump preferred — no rate limits, weekly refresh)
  • Confirm gmr_id UUID5 scheme
  • Spike: stand up a local Neo4j instance and load 20 EU companies manually to validate Cypher queries match what the API needs
PHASE 1 Infrastructure

Deploy Neo4j to the k8s cluster.

  • Add Neo4j Helm chart to infra/ (community edition, single node for now)
  • PVC for Neo4j data on NFS or local SSD (graph data is not large — ~1 GB for current dataset)
  • Neo4j browser accessible internally for development
  • Connection credentials in k8s Secret, consumed by edgar-gmr-etl
  • Smoke test: connect from edgar-gmr-etl pod, run RETURN 1
PHASE 2 ETL — Load Current Data into Graph

Three sources to ingest, in dependency order.

2a. Company master (GLEIF full dump)

  • Download GLEIF Level 1 concatenated file (published daily, ~500 MB CSV)
  • Extract: LEI, legal name, country, legal form, entity status
  • Generate gmr_id from lei:{LEI}
  • MERGE (:Company {gmr_id}) — idempotent, safe to re-run weekly
  • This establishes the authoritative company record for all entities with a LEI

2b. EU listings and financials (eu_entities.json + summaries/)

  • For each entry in eu_entities.json: find or create Company node by LEI, create Listing node, MERGE [:LISTED_AS]
  • For each summaries/{TICKER}.json: find Company by LEI, create FinancialYear nodes per year, MERGE [:REPORTED]
  • Companies whose LEI is in the GLEIF dump will already exist from 2a; this step adds listings and financials

2c. US companies and financials (EDGAR)

  • For each entry in company_tickers.json: generate gmr_id from edgar:{CIK}, MERGE (:Company {gmr_id})
  • Set cik, name, country: "US", create Listing node, MERGE [:LISTED_AS]
  • Fetch annual financials via edgartools (income statement, balance sheet, cash flow) and store as FinancialYear nodes with source: "EDGAR"
  • Same schema as EU: revenue, gross_profit, operating_income, net_income, ebitda, eps, total_assets, total_debt, equity, cash, capex
  • Batch ETL job — run once to seed, then refresh periodically via cronjob
  • ~10,000 companies; parallelised and checkpointed the same way ESEF summaries are

2d. Price index

  • No change to CSV files or _index.yml
  • The API resolves: Company → [:LISTED_AS] → Listing.ticker → CSV file path
PHASE 3 API Adapter — GraphDataSource

New implementation of FinancialDataSource backed by Neo4j + NFS. The existing abstract class is exactly the right seam.

New module layout inside edgar-gmr-etl:

src/data/graph/
  graph_data_source.py    # implements FinancialDataSource
  neo4j_client.py         # connection pool, retry, Cypher helpers
  price_reader.py         # reads CSV from NFS (reuse existing logic)

Method mapping:

Interface methodBackend
get_annual_fundamentals(ticker)Cypher: MATCH (:Listing {ticker})<-[:LISTED_AS]-(c)-[:REPORTED]->(f) RETURN f ORDER BY f.year DESC
get_price_history(ticker, period)Read CSV from NFS (unchanged)
get_annual_avg_prices(ticker)Aggregate from CSV (unchanged)
get_market_snapshot(ticker)Graph for company metadata + CSV for price
get_available_tickers()Cypher: MATCH (l:Listing) RETURN l.ticker, l.exchange
search_tickers(query)Full-text index on Company.name + Listing.ticker

RoutingDataSource is retired once GraphDataSource is fully operational — the graph handles both EU and US from the same query path.

  • Implement GraphDataSource with full test coverage against a test Neo4j container
  • Run in parallel with existing data sources (feature flag or config toggle) to validate parity
  • Decommission RoutingDataSource, EsefDataSource, EdgarDataSource once parity confirmed
PHASE 4 UI Adaptation

Expected to be minimal — API contracts are unchanged, frontend sees no difference.

  • Audit every gmr-web API call — confirm all use ticker as the entity key
  • Company search improves automatically: Neo4j full-text index beats current substring match on flat lists
  • Add stable company URL route by gmr_id (e.g. /company/{gmr_id}) alongside /{ticker} — optional now, required later for multi-listed companies

What Does Not Change

  • Price CSV format and NFS layout
  • _index.yml price index
  • All API response schemas
  • The FinancialDataSource interface contract
  • The gmr-web frontend (Phase 4 changes are additive, not breaking)
  • The ESEF and price-fetcher cronjobs (they continue writing to NFS as-is)

Open Questions for Discussion

  1. GLEIF full dump cadence. GLEIF publishes daily. Do we refresh the Company master weekly (cronjob) or on-demand?
  2. Neo4j Community vs Enterprise. Community is single-node. Is that acceptable long-term or do we plan for clustering from the start?
  3. Parallel running period. How long do we run GraphDataSource alongside the existing sources before cutting over? Suggest: until all known tickers return identical responses.
