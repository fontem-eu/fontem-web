Vision: Follow the Money

The graph now knows who companies are and what they earn. The next layer is who pays them with public money, how much, and for what.

EU public procurement is one of the largest economic activities in Europe — over €670 billion per year flows through government contracts. This data is public, structured, and machine-readable. By connecting it to our company graph, we build a comprehensive EU enterprise knowledge base that can answer questions like:

  • Which companies receive the most public money in a given country?
  • Which government bodies are the biggest spenders?
  • Are contracts being awarded through open competition or negotiated procedures?
  • How do a company’s government revenues compare to its total revenue?
  • What sectors does public spending concentrate in?
Long-term direction

This is one step toward the broader vision — a comprehensive EU enterprise knowledge graph connecting companies, people, political roles, and public records. Procurement data is the natural starting point: it’s the most structured, most complete, and most immediately useful. No judgements of character — just data, traceable back to official EU sources.

Data Source: TED (Tenders Electronic Daily)

TED is the EU’s official procurement database. Every EU government contract above a threshold value (€140K for services, €5.4M for works) must be published here.

Access methods

  • Bulk XML downloads (preferred — same approach as GLEIF, no rate limits): https://ted.europa.eu/packages/monthly/YYYY-M
  • REST API at api.ted.europa.eu (anonymous, for targeted queries)
  • CSV subset at data.europa.eu (simplified, fewer fields)

Format: eForms XML (EU-mandated standard since October 2023). Pre-2023 data uses an older TED XML schema.

Key insight: All the “juicy” metadata — who won, how much, from whom, for what — is in the structured XML. We never need to download or parse legal PDFs.

Company Matching Strategy

This is the hardest part. TED identifies companies by name + VAT. Our graph identifies by LEI. We match in five layers, from highest to lowest confidence:

1

VAT direct match (cached)

If a Company node already has vat = {vat_number} (set by a previous ETL run), link directly. O(1) index lookup. This is the fast path for re-runs — once a VAT is matched, it never needs to be resolved again.

2

VIES validation + enrichment

The EU’s VAT Information Exchange System provides a free REST API that validates VAT numbers and returns the registered legal name and address:

GET https://ec.europa.eu/taxation_customs/vies/rest-api/ms/{CC}/vat/{number}
→ { isValid, name, address, countryCode }

When a contractor’s VAT is present in TED data, we query VIES to get the canonical legal name. This dramatically improves Layer 4 name matching — TED often has abbreviated or localized names, while VIES returns the official registered name.

VIES limitations:
  • Germany and Spain return valid/invalid only — no name or address (privacy rules)
  • Unreliable: ~30% downtime for some countries (BE, DE). Queries must have retry logic + backoff
  • No bulk API: one VAT at a time, undisclosed rate limits. Aggressive polling triggers IP bans
  • ToS grey area: officially restricted to “persons involved in intra-Community supply” — using it for data enrichment is not explicitly permitted
  • All 27 EU states + Northern Ireland (XI). No UK (post-Brexit), Norway, or Switzerland

Practical approach: Use VIES as a targeted enrichment tool, not a bulk scraper. Query only for contractors that didn’t match on Layer 1. Cache results permanently on the Company node (vat, vies_name). Rate-limit to ~1 req/3s with exponential backoff. Accept that DE and ES contractors won’t get VIES names — fall through to Layer 3.

Verified experimentally: GET .../rest-api/ms/PT/vat/509083668 returned "name": "RCPOOL LDA" with full address. Spanish VAT A82018474 (Telefonica) returned "name": "---". Germany: same blindness. VIES works well for ~22 of 27 EU countries.

3

GLEIF registration lookup

Query api.gleif.org by registration number to find the LEI for a given VAT. If found, match to the existing Company node and set vat for future runs. The GLEIF Level 2 “Registration Authority” data maps national IDs to LEIs. Cache results.

4

Fuzzy name matching (Neo4j full-text + Dice similarity)

When layers 1–3 fail, fall back to name matching. This is a two-stage process:

  1. Normalize: strip legal suffixes (AG, GmbH, S.A., Ltd, B.V. — ~200 known suffixes via cleanco library), transliterate accents via unidecode, collapse whitespace. Store as name_normalized on both sides.
  2. Retrieve candidates: Neo4j full-text index with Lucene fuzzy (~) on name_normalized, filtered by country. Returns 5–50 candidates in ~10ms.
  3. Score: apoc.text.sorensenDiceSimilarity() on normalized names. Auto-match at >0.85, flag for review at 0.6–0.85, no match below 0.6.
CALL db.index.fulltext.queryNodes('companyNameIndex', $name + '~')
YIELD node, score
WHERE node.country = $country AND score > 0.3
WITH node,
     apoc.text.sorensenDiceSimilarity(
       $name_normalized, node.name_normalized
     ) AS dice
WHERE dice > 0.85
RETURN node ORDER BY dice DESC LIMIT 1
Why not embeddings? Character n-gram methods (Dice) get 85–90% F1 on company name matching. Transformer embeddings get 88–93%. The 3–5% gap doesn’t justify running a separate model service. The normalization step (stripping suffixes) does most of the heavy lifting. Embeddings remain a future enhancement for cross-lingual cases (“Deutsche Bank” vs “Banco Alemán”) if needed.
5

Create new Company node

Unmatched contractors become new nodes via gmr_id.from_national_id(country, vat) (preferred if VAT available) or gmr_id.from_name(country, name) (last resort). These exist purely from procurement data — linkable later when they appear in GLEIF or via future deduplication runs.

Expected match rate: ~20% of unique contractors will match existing GLEIF Company nodes on Layers 1–3. Layer 4 (fuzzy name) adds another ~10–15%. The remaining ~65% become new Company nodes — mostly small local firms not in GLEIF. But the matched companies represent the bulk of contract value.

VIES fallback: what about DE and ES?

Identity Resolution: The gmr_id Conflict

The problem, explained

gmr_id is a deterministic hash (UUID5 = SHA-1 of a namespace + input string). Different inputs produce different hashes — even for the same real-world company:

# Same company, two different gmr_ids:
uuid5(NAMESPACE, "lei:724500973ODKK3IFQ447")  →  a4cb9465-956e-...   (from GLEIF)
uuid5(NAMESPACE, "NL:ADYEN N.V.")             →  f83d1a02-7b4e-...   (from TED, no LEI available)

# Two Company nodes exist. Both are Adyen N.V. One has financials, one has contracts.

This happens when a company enters the graph from TED (matched by name, Layer 5) and is later confirmed to be the same entity as an existing GLEIF company.

Resolution strategy: [:SAME_AS] + operator review + merge

Step 1: Detect candidates

  • Periodic batch job (after each major load) finds Company pairs with same LEI, same VAT, or same normalized name + country but different gmr_id
  • Creates [:SAME_AS {confidence, method, detected_at, reviewed: false}] relationship from the lower-priority node to the canonical one
  • Direction: name-based node → SAME_AS → LEI-based node (LEI always wins)

Step 2: Auto-merge or flag

  • Trivial merge (automatic): if all shared properties have identical values (or one side is null), merge immediately via apoc.refactor.mergeNodes(). No operator needed. This handles: same LEI on both nodes, or same VAT with no conflicting name/country.
  • Conflicting merge (manual): if any shared property has different non-null values (e.g., different names, different countries), flag for operator review. The [:SAME_AS] relationship stays with reviewed: false.
  • Operator queue: MATCH (dup)-[r:SAME_AS {reviewed: false}]->(canonical) RETURN ...
  • Operator actions: approve (merge, picking canonical values), reject (not the same entity), or defer
  • Initially: Cypher script or Jupyter notebook. Later: simple review page in gmr-web

Step 3: Execute merge

  • Use apoc.refactor.mergeNodes([canonical, duplicate], {properties: "combine", mergeRels: true})
  • The canonical node (LEI-based) survives. All relationships from the duplicate (contracts, listings) are transferred
  • Before merge: create a (:MergeEvent {canonical_id, merged_id, merged_at, method, properties_before}) audit node
  • After merge: explicitly set gmr_id to the canonical value (LEI-based wins)
# Priority for canonical gmr_id:
# 1. lei:{LEI}              ← highest (from GLEIF, globally unique)
# 2. edgar:{CIK}            ← US companies
# 3. {ISO2}:{VAT}           ← from TED procurement data
# 4. {ISO2}:{NAME_UPPER}    ← last resort

# When sources meet, higher priority always wins
Prevention over cure: The TED ETL should always attempt identifier-based lookup (LEI, VAT) before creating a name-based node. This prevents the majority of duplicates. The SAME_AS workflow is the safety net for what slips through.

PHASE 6 ETL Pipeline — eForms Parser as a Library

No Python library for parsing eForms XML exists. We build one with clean interfaces, designed for reuse.

Prior art

Investigated: OP-TED/eForms-SDK (schema only, no parser), eforms-core-java (Java, metadata only), bjornjorgensen/TED-and-Doffin-to-ocds (Python, 545 XPath converters — best reference, but outputs OCDS and is not packaged). Nothing on PyPI or npm. We build our own.

What is eForms XML?

Every TED notice is an XML file following the EU’s eForms schema (UBL 2.3 + EU extensions). A Contract Award Notice contains: the contract metadata (title, value, CPV, dates), an organizations block (all parties defined by ID), and a results block that links lots → tenders → winning contractors by referencing those org IDs. The parser’s job is to resolve these indirections and yield flat, structured records.

Library architecture

src/eforms/                          # standalone library — no Neo4j, no GMR dependencies
  __init__.py
  namespaces.py                      # XML namespace map (UBL + EU extensions)
  models.py                          # dataclasses: Notice, Contract, Organization, Lot, Award
  parser.py                          # main entry: parse(xml_stream) → Notice
  extractors/                        # one module per concern, each returns a dataclass
    __init__.py
    notice_metadata.py               # BT-701, publication number, notice type, dates
    procedure.py                     # procedure type, title, description
    organizations.py                 # all orgs: name, VAT, country, address → dict[id, Organization]
    lots.py                          # lot-level: title, CPV, estimated value
    awards.py                        # results: lot→tender→contractor mapping, award values
  filters.py                         # filter notices by type (award only, modifications, etc.)
  stream.py                          # iterate ZIP archive, yield parsed Notice objects

src/etl/                             # GMR-specific ETL (depends on src/eforms + Neo4j)
  load_cpv.py                        # one-time CPV taxonomy load
  ted_matcher.py                     # company matching (layers 1-5)
  load_ted_contracts.py              # main ETL: download → parse → match → MERGE

Key interfaces (dataclasses)

@dataclass
class Organization:
    org_id: str           # internal eForms ID (e.g. "ORG-0001")
    name: str             # legal name
    country: str          # ISO 3166-1 alpha-2
    legal_id: str | None  # VAT / national reg number (from cbc:CompanyID)
    address: str | None

@dataclass
class Award:
    lot_id: str
    contractor_org_id: str       # references Organization.org_id
    value: float | None
    currency: str | None
    award_date: str | None       # ISO date

@dataclass
class Notice:
    notice_id: str               # BT-701 UUID
    publication_number: str      # e.g. "291298-2024"
    notice_type: str             # "can-standard", "can-modif", etc.
    title: str
    description: str | None
    cpv_main: str | None
    procedure_type: str | None
    issue_date: str
    buyer_org_id: str            # references Organization.org_id
    total_value: float | None
    currency: str | None
    organizations: dict[str, Organization]  # org_id → Organization
    lots: list[Lot]
    awards: list[Award]

    def buyer(self) -> Organization:
        return self.organizations[self.buyer_org_id]

    def contractors(self) -> list[Organization]:
        return [self.organizations[a.contractor_org_id] for a in self.awards]

Usage

from src.eforms.stream import stream_notices
from src.eforms.filters import awards_only

# Parse a monthly ZIP, yield only Contract Award Notices
for notice in awards_only(stream_notices("/tmp/ted-2024-06.zip")):
    print(notice.title, notice.total_value)
    for award in notice.awards:

Why a library? The eForms XML structure is complex (indirections, lot nesting, org references). By isolating the parser from the ETL, we get: testable extraction logic (mock XML in, dataclass out), reusable for future notice types (PINs, modifications, completions), and a clean seam between “understand XML” and “load into Neo4j.”

Consistent with the established project conventions: smallest tests possible, public-API-oriented, mock at the boundary, no network in unit tests.

The src/eforms/ library is the most testable part of this plan. Pure dataclass extraction from XML — no database, no network, no state. Each extractor gets its own test file with crafted XML fixtures. This is where we invest the most testing effort because parser bugs have the highest blast radius (every contract loaded with wrong data).

Keeping Data Fresh

TED publishes one OJ S (Official Journal Supplement) issue per weekday — about 250 issues/year. Each daily package contains all notices published that day, including new contract awards, corrections to old notices, and contract modifications.

What a daily package contains

  • ~2,800–3,200 notices per day (all types combined), 50–200 MB compressed
  • New notices: fresh contract notices, award notices, PINs
  • Change notices (corrigenda): corrections to previously published notices — published as new notices with their own ID, referencing the original via BT-758. They contain the full consolidated text (not a diff)
  • Contract modifications: value changes, scope changes — separate notice type (can-modif)

ETL update strategy

DAILY CRONJOB Incremental contract loader

Runs daily at 06:00 UTC (after TED publishes the morning OJ S issue):

  1. Fetch the previous day’s OJ S package (or query the Search API by publication-date)
  2. Filter to award notices (can-standard, can-social) and modifications (can-modif)
  3. For each notice: parse XML, match company, MERGE Contract node by ted_notice_id
  4. For change notices: look up the original Contract by referenced BT-758, update its properties with the consolidated text
  5. For modifications: update the Contract node’s value_eur and add a modified_date property
Idempotent by design. MERGE on ted_notice_id means processing the same day twice is harmless. Change notices carry consolidated text, so the latest version always wins via SET.

Contract value tracking

A contract’s value can change after award (modifications are common in public procurement). Our strategy:

  • The Contract node stores the current value (value_eur), overwritten by the latest modification
  • The original award value is preserved in value_original_award (set once, never overwritten)
  • A modification_count property tracks how many times the contract was modified
  • The full modification history can be reconstructed from TED if needed (each modification is a separate notice)

What Will Break

An honest assessment of what can fail, and especially what won’t age well as data and complexity grow.

Near-term risks

1. Company matching will produce garbage for small contractors.

Layer 5 (name-based gmr_id) is deterministic but fragile. “CONSTRUCCIONES GARCIA S.L.” and “GARCIA CONSTRUCCIONES S.L.” produce different gmr_ids → duplicate Company nodes. This is the single biggest data quality risk. It’s manageable at low volume but will compound as we load more years.

Mitigation: Accept duplicates for now. Build a periodic deduplication job that merges Company nodes with the same VAT but different gmr_ids. Log all Layer 5 creations for manual review of high-value contracts.

2. VIES will be down when we need it.

~30% downtime for DE/BE. Germany is the largest EU procurement market. Every daily ETL run will have a batch of contractors it cannot validate.

Mitigation: Never block ETL on VIES. Queue failed VIES lookups for retry in the next run. A “vies_pending” flag on the Company node triggers re-validation on the next pass.

3. eForms XML schema is not uniform across years.

Pre-October 2023 data uses the old TED XML schema (different structure, different field names). If we backfill to 2018, we need two parsers. The old schema is less well-documented and more variable across countries.

Mitigation: Start with 2024+ (pure eForms). Add the legacy parser only when historical data is explicitly needed.

What won’t age well

4. get_available_tickers() scans all Listing nodes.

Currently returns 17K listings. Fine. Once we create Company nodes for procurement contractors (potentially 100K+ new companies), we must not let those leak into the ticker search. GraphDataSource must filter to WHERE l.active = true, but as node count grows, full scans will slow down.

Mitigation: Ensure only companies with listings appear in ticker search. Procurement-only companies (no ticker) should never be returned by get_available_tickers(). The current Cypher already does MATCH (c)-[:LISTED_AS]->(l), so this is safe as long as we never create fake Listing nodes for procurement-only companies.

5. Neo4j single-node will hit memory limits.

Current heap: 512m–1g, page cache: 512m. With 3.26M companies + 1.7M contracts + relationships, the working set approaches 2–3 GB. Queries that traverse large subgraphs (e.g. “all contracts for companies in sector X”) will pressure the page cache.

Mitigation: Monitor Neo4j memory via Prometheus. Increase PVC and pod memory limits proactively (the k8s node has 8 Gi limit available). The community edition’s single-node constraint is fine for our scale; we don’t need clustering.

6. Authority deduplication is a rabbit hole.

“Bundesministerium des Innern und für Heimat” vs “BMI” vs “Federal Ministry of the Interior” — all the same authority, three different names in TED data across different notices and languages. Naive name-based Authority IDs will fragment badly.

Mitigation: Accept initial fragmentation. Add a manual mapping table (CSV of authority aliases) that the ETL consults. Iterate on this as patterns emerge from real data.

7. Contract value accuracy is inherently messy.

TED contract values are self-reported by contracting authorities. They may represent: estimated value, maximum framework value, individual lot value, or total award value. Different countries interpret “value” differently. Modifications can make the original value meaningless.

Mitigation: Always store both value_original_award and current value_eur. Display both in the UI. Never aggregate contract values across countries without a disclaimer. Framework agreements should be flagged separately (their “value” is a ceiling, not actual spend).

8. Daily ETL at scale: 3,000 notices/day × 365 × 8 years = reprocessing debt.

If a parser bug is found after months of daily loading, we need to reprocess all affected notices. Reprocessing years of data takes hours and puts load on Neo4j.

Mitigation: Keep the raw XML packages on disk (or NFS) as an immutable audit log. The ETL should be able to re-run against local files. Add a loaded_at timestamp on Contract nodes to identify what needs reprocessing.

Open Questions

  1. Start year. Begin with 2024+ only (eForms format, cleanest data), or go back to 2018 (different XML schema, requires a second parser)?
  2. GLEIF registration authority file. Layer 3 queries GLEIF per-VAT. Should we batch-download the GLEIF Registration Authorities file instead (avoiding rate limits, same approach as Level 1 dump)?
  3. VIES usage policy. The ToS say “for persons involved in intra-Community supply.” Are we comfortable using it for enrichment? Should we limit to high-value contractors only?
  4. Contract thresholds. TED only covers above-threshold contracts (€140K services, €5.4M works). Smaller contracts are in national portals. Is TED-only sufficient for v1?
  5. Authority deduplication. Government bodies change names across languages and abbreviations. Accept fragmentation initially and clean up later, or invest in a mapping table upfront?
  6. Framework agreements. These have a “maximum value” that is a ceiling, not actual spend. Should they be loaded alongside regular awards, or flagged/excluded?
  7. Raw XML retention. Should we keep downloaded TED XML packages on NFS as an immutable audit log for reprocessing, or delete after loading?

Critical Self-Review

Stepping back from the plan and asking: what’s really going to happen when we build this?

Things this plan gets right

  • Data source choice. TED bulk XML is the right approach — same pattern as GLEIF, proven in production, no rate limits, idempotent.
  • Incremental daily updates. The daily OJ S packages + MERGE by notice ID is clean. No reconciliation needed.
  • Conservative matching thresholds. Auto-match at >0.85 Dice and creating new nodes for everything else means we won’t merge different companies. Duplicates are fixable; wrong merges are catastrophic for a knowledge base.
  • Company-ID-first API. Moving from /{ticker} to /companies/{gmr_id} is the right architectural direction. The ticker-based API was always a concession to the “stock screener” origin.

Things this plan underestimates

The eForms XML parser will take 3x longer than expected.

The eForms schema is large and complex. Contract awards can have multiple lots, each with different winners. Lot structures vary wildly across countries. The “extract title, value, contractor” step that looks simple on paper will require handling dozens of edge cases: missing values, multi-currency lots, joint ventures (multiple contractors per lot), framework agreements vs individual contracts. Budget at least a full session just for the parser.

The GLEIF ↔ TED company overlap might be worse than 20%.

GLEIF has 3.26M entities, but most are financial entities (banks, funds, holding companies) that must have a LEI for regulatory reasons. EU procurement contractors are construction firms, IT consultancies, logistics companies — many of which never obtained a LEI. The actual overlap might be 10–15%, not 20%. We should measure this empirically with 1 month of data before committing to the matching strategy.

The API migration from ticker to gmr_id will break the frontend.

The Vue SPA routes are ticker-based (/AAPL/summary, /GALP.LS/fundamentals). Adding /company/{gmr_id} routes alongside is fine, but making contracts only accessible via gmr_id means the frontend needs a way to resolve ticker → gmr_id before it can fetch contracts. This resolution step needs to be fast (cached, or embedded in the initial page load). Don’t underestimate the frontend plumbing here.

Things this plan ignores

No consideration of sub-threshold procurement.

TED covers contracts above EU thresholds. For many companies (especially SMEs), the most interesting contracts are below threshold and published only on national portals. This plan gives us a partial picture. We should be explicit in the UI about what’s covered: “EU public contracts above €140K (services) / €5.4M (works).”

Unresolved concerns

  1. How do we test matching quality at scale? We can unit-test the matching code, but validating that “SIEMENS AKTIENGESELLSCHAFT” in TED correctly matches “Siemens Aktiengesellschaft” in GLEIF requires ground truth. Do we manually verify a sample? How large?
  2. What happens when a Company node created from procurement data later appears in GLEIF? Addressed above in Identity Resolution — the [:SAME_AS] + merge workflow handles this. But the periodic detection job needs to run after every GLEIF refresh, not just after TED loads.
  3. The search experience is about to get worse before it gets better. If procurement-only companies (no listing, no financial data) appear in search results, users will click on them and see an empty profile. We need to either suppress them from search or build a procurement-centric company profile page before launching.
