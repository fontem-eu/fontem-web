N1: Hierarchical Navigation

N1 Replace flat tab bar with grouped navigation

Problem

9 views in a flat row. Overflows on mobile. Unscalable as features grow.

Proposed structure

Overview
  ├── Profile          (company card + directors + contracts + group)
  └── Graph Explorer   (interactive entity graph)

Financials
  ├── Summary          (price chart + key stats)
  ├── Fundamentals     (ratio table)
  ├── Income / Cash Flow / Balance / Valuation

Procurement
  └── Contracts        (sortable table with TED links)

Analysis
  └── GMR Long         (value investing screen)

UX

  • Desktop: Two-level. Top: category pills. Below: sub-views for active category.
  • Mobile: Single dropdown: “Financials › Income”. Compact, no overflow.
  • URLs unchanged: /c/:ticker/:view. Hierarchy is purely UI.

Test impact

  • DataViewSelector.test.js: rewrite for grouped nav + mobile dropdown
  • data-view.spec.js (e2e): update selectors
  • responsive.spec.js (e2e): verify dropdown

N2: Interactive Graph Explorer

N2 Entity relationship graph — any entity type as entry point

Entry points

The graph explorer works from any entity, not just companies:

  • Company: shows subsidiaries, contracts, directors, authorities
  • Authority: shows all companies it awarded contracts to, contract values
  • Person: shows all companies they direct, and those companies’ contracts
  • Contract: shows the awarding authority, winning company, CPV sector

Technology: Cytoscape.js

Force-directed layout, filtering, pinning, events. ~170 KB gzipped.

API

GET /api/graph/{entity_id}?depth=1&types=Company,Contract,Person,Authority

// entity_id can be:
//   gmr_id (Company), authority_id, person_id, ted_notice_id, cpv code
// The API detects the type from the ID format or a ?type= param

Response:
{
  "center": { "id": "...", "label": "SOCOMEC", "type": "Company" },
  "nodes": [...],
  "edges": [...],
  "truncated": false,
  "total_available": 42
}

Controls

ControlBehavior
Depth slider (0–3)Re-fetches from API. Default: 1.
Type filters (checkboxes)Client-side show/hide. All checked by default.
Keyword filter (text)Client-side, matches node labels instantly.
Lock node (right-click / toggle)Survives filter changes. Pinned position. Lock icon.
Click nodeTooltip with details + “Go to profile” + “Set as center”.

Node styling

Company    → circle, blue,   size ~ contract count
Contract   → diamond, amber, size ~ value_eur
Authority  → hexagon, green
Person     → triangle, purple
CPV        → small dot, grey

Performance

  • API caps at 500 nodes, returns truncated: true + total_available
  • Type filter applied server-side in Cypher WHERE
  • REPORTED and LISTED_AS hidden by default

N2a: Path Finding Between Entities

N2a “How is entity A connected to entity B?”

Concept

The user picks two entities (e.g., a Person and an Authority) and the system shows all paths connecting them. Not just the shortest — also near-shortest paths that reveal alternative connections.

UX flow

  1. User opens graph from any entity (the “source”)
  2. Clicks a “Find path to...” button in the toolbar
  3. A search box appears. User types a name or picks from the graph.
  4. The API returns paths. The graph highlights them.

API endpoint

GET /api/graph/paths?from={id_a}&to={id_b}&max_depth=5&extra=2

Response:
{
  "from": { "id": "per-012", "label": "Jean Dupont", "type": "Person" },
  "to": { "id": "auth-789", "label": "Ville de Paris", "type": "Authority" },
  "paths": [
    {
      "length": 2,
      "nodes": ["per-012", "gmr-123", "con-456", "auth-789"],
      "edges": [
        { "source": "per-012", "target": "gmr-123", "type": "DIRECTS" },
        { "source": "auth-789", "target": "con-456", "type": "AWARDED" },
        { "source": "con-456", "target": "gmr-123", "type": "AWARDED_TO" }
      ]
    },
    {
      "length": 3,
      "nodes": ["per-012", "gmr-345", "con-999", "auth-789"],
      "edges": [...]
    }
  ],
  "shortest_length": 2
}

Path query strategy

// Find shortest path
MATCH path = shortestPath(
  (a {gmr_id: $from})-[*..10]-(b {gmr_id: $to})
)
RETURN path

// Find additional paths up to shortest + extra hops
MATCH path = (a {gmr_id: $from})-[*..($shortest + $extra)]-(b {gmr_id: $to})
WHERE length(path) <= $shortest + $extra
RETURN path
ORDER BY length(path)
LIMIT 10

UI: path highlighting

  • Shortest path highlighted in bold blue
  • Alternative paths in lighter blue with dashes
  • Non-path nodes dimmed to 30% opacity
  • Path legend: “3 paths found. Shortest: 2 hops. Longest shown: 4 hops.”
  • Click a path in the legend to highlight just that one
Why “shortest + extra” instead of all paths: Finding all paths in a graph with 3.4M nodes is combinatorially explosive. The extra parameter (default: 2) limits exploration to paths within 2 hops of the shortest, which catches interesting alternative routes without blowing up.

N2b: Temporal Dimension

N2b Time-aware graph exploration

Concept

Every relationship in the graph has a time component: contracts have award dates, directors have start/end dates, subsidiaries form and dissolve. A timeline control lets the user see the graph as of a specific date, revealing how relationships evolved.

UI: timeline slider

┌──────────────────────────────────────────────────────────┐
│  2020     2021     2022     2023     2024     2025       │
│  ├────────┼────────┼────────┼────────┼────────┤         │
│                              ▲                           │
│                         [Apr 2023]                        │
│                                                          │
│  ● 3 contracts awarded  ● 2 directors active  ● 1 sub   │
└──────────────────────────────────────────────────────────┘
  • Range: min(earliest date in the graph) to today
  • Granularity: month. Snap to month boundaries.
  • Mode: “as of date” — shows only relationships that existed at the selected point in time:
    • Contracts: award_date <= selected_date
    • Directors: start_date <= selected_date AND (end_date IS NULL OR end_date >= selected_date)
    • Subsidiaries: always shown (GLEIF doesn’t have dissolution dates in our data)
  • Play button: auto-advances the slider by 1 month per second, animating the graph growth over time
  • Stats bar: below the slider, shows counts at the selected date (contracts awarded, directors active, subsidiaries)

Implementation approach

Client-side filtering, not server re-fetch.

The API returns all edges with their date fields. The timeline slider filters edges client-side by comparing dates. This avoids an API call on every slider move. Cytoscape supports ele.hide() / ele.show() with ~1ms latency per element.

Caveat: this only works if the graph is already loaded (depth is set). Changing depth still triggers a server fetch. The timeline operates within the already-fetched data.

API changes

The graph API response already includes date fields on edges. We just need to ensure they’re present:

// Edge objects gain a date field
{
  "source": "auth-789", "target": "con-456", "type": "AWARDED",
  "date": "2024-06-15"    // award_date for contracts
}
{
  "source": "per-012", "target": "gmr-123", "type": "DIRECTS",
  "start_date": "2020-01-01", "end_date": null  // active director
}

Visual design

  • Nodes that have no edges at the selected date fade to 10% opacity (they exist but aren’t connected yet)
  • New edges appearing at the selected date flash briefly with a glow animation
  • The “play” mode uses requestAnimationFrame for smooth 1-month/second advancement

Complexity assessment

This is a session 5+ feature. The timeline slider, date filtering, play animation, and edge date extraction are each non-trivial. Recommend implementing the core graph explorer (N2) first, then adding temporal as an enhancement. The API should return dates from the start so no API changes are needed later.

N2c: Edge Bundling & Export

N2c Aggregate edges + SVG/JSON export

Edge bundling

When a company has 200 contracts from the same authority, showing 200 individual edges is visual noise. Instead:

  • If >5 edges exist between the same two nodes with the same type, bundle them into a single weighted edge
  • Bundled edge label: “47 contracts · €12.3M”
  • Edge thickness proportional to count or total value
  • Click the bundled edge to expand into individual edges (or show a list)
  • Toggle: “Bundle edges” checkbox in controls (on by default)

Implementation

Bundling is done client-side after the API response arrives. The API returns individual edges. The GraphExplorer component groups them before passing to Cytoscape:

// Group edges by (source, target, type)
const bundled = groupBy(edges, e => `${e.source}-${e.target}-${e.type}`)
for (const [key, group] of bundled) {
  if (group.length > 5) {
    // Replace with a single weighted edge
    yield { ...group[0], weight: group.length, totalValue: sum(group, 'value_eur') }
  } else {
    yield* group  // show individually
  }
}

Export

FormatUse caseImplementation
SVGReports, presentationscy.svg() — built into Cytoscape
PNGQuick sharingcy.png() — built into Cytoscape
JSONFurther analysis, reimportcy.json() for graph state, or raw API response

Export buttons in the toolbar: [SVG] [PNG] [JSON]. Downloads to the user’s browser.

N2d: Saved Views & Bookmarks

N2d Save, share, and restore graph states

Concept

An investigator finds an interesting subgraph. They want to save it, share it with a colleague, and come back to it later. This is the foundation for the future report builder (embedding visualizations in documents).

What gets saved

{
  "center_id": "gmr-123",
  "depth": 2,
  "type_filters": ["Company", "Contract", "Authority"],
  "keyword": "",
  "locked_nodes": ["gmr-345", "auth-789"],
  "node_positions": { "gmr-123": [100, 200], "gmr-345": [300, 150] },
  "timeline_date": "2024-06-01",   // null if timeline not active
  "path_target": null,              // or entity_id if path mode active
  "name": "Mota-Engil procurement network"
}

Storage options

OptionProsCons
URL hash (#state=base64)Shareable, no backendURL length limit (~2KB), no persistence
localStoragePersistent, no backendNot shareable, per-device
Neo4j (:SavedView) nodePersistent, shareable, queryableNeeds API endpoint
Recommendation: localStorage for v1, Neo4j for v2.

Start with localStorage (list of saved views in the sidebar). Add a “Copy link” button that encodes the state in the URL hash. Later, when the report builder exists, migrate to Neo4j storage for cross-user sharing.

UI

  • “Save view” button in the toolbar → prompts for a name
  • Saved views listed in a collapsible sidebar panel
  • Click a saved view to restore: center, depth, filters, locks, positions
  • “Copy link” button encodes the state in the URL for sharing
